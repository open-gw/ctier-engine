# 10 — the release half of Tier 3

Withhold returns `202`. A named approver posts a decision. On approval,
custody rebuilds method, request target, query and body, presents its
own credential, and the backend sees that — plus attribution headers it
must not authorise on. The agent asked once and was not asked again.

Live: one withheld PUT, one approval, one execute against the echo.
The echo carried `Authorization: Bearer custody-service-v1`,
`x-ctier-agent`, `x-ctier-approver`, `x-ctier-correlation-id`, the
stored idempotency key, and not the agent's bearer token.

## C8 is recorded, not produced

Rejection writes correlation id, approver, timestamp, operation class,
and stops. It does not pause the agent. Suspension is a property of the
credential at the authorisation layer, and that layer is not here.

Tier 4's `423` and C8's rejection now both claim an effect nothing
produces, and they are waiting on the same component. Simulating the
pause by having Kong ask custody "is this agent paused?" on each
request is forbidden by name in 1.1.7: it satisfies the letter and
undoes the architecture. The plugin still has one network call, and
it is still `POST /v1/pending`.

Expiry is the other C8 branch and it does run: lazy, on read, against
a clock parameter. An expired row and a rejected row are different
records. One has no approver; the other has a named person who looked.

## C6 as scoped in 1.1.7

Sufficient for the credential question. Byte-identity of method, target,
query and body is exactly what was rebuilt. The service token is added;
the agent token is not present to add.

Still decided here, not in the criterion:

- The attribution header names (`x-ctier-agent`, `x-ctier-approver`,
  `x-ctier-correlation-id`). C6 says they are recorded; it does not
  put them on the wire. They are a claim from a caller authenticated
  as the policy service. A backend may log them. It must not make an
  access decision on them.
- Execution addresses the backend, not the gateway. Sending the rebuilt
  request back through Kong would withhold it again. C6 does not say
  that; the withhold path does.
- The approval is claimed (`pending` → `executing`) before the HTTP
  call, so a second approval cannot sneak a second execute.

None of those is a prohibition whose omission points the unsafe way.
The unsafe reading of C6 was storing the agent token. 1.1.7 closed it.

## C7, C9, C10

C5, C6 and C7 have each had a gap whose plain reading points the unsafe
way. C7 was the one this task actually built against.

**C7.** First use for its purpose: the derived key rides on the executed
request as `Idempotency-Key`, so a duplicate decision event cannot
double-execute at the backend. The key used is the one stored at persist,
not a re-derivation. C7 does not name the on-the-wire field, and it does
not say "do not re-derive at execute from the live request." Re-deriving
from "the request specifics" is the envelope trap again — an implementer
completing the derivation could hash `Authorization`. Using the stored
key avoids that without C7 having forbidden it. The backend is not
required, by C7, to honour the header; we send it where one is accepted.

**C9.** Not built against. Kong still emits `423` and nothing suspends
the agent. The criterion forbids a resume under the agent's identity;
we did not add one. That is the same shape as C5 before `pollUrl` was
named: the letter does not forbid a handoff URL on the `423` inviting
the agent to watch the human. "It looks fine" is what was true of C5.

**C10.** The decision is recorded (named approver, timestamp, claim to
`executing`) before the backend is called. That reading was enough.
The record lives on the pending row; the ledger formats are task 11.
The unsafe reading — execute, then write the decision only if it
succeeded — would hide a failed high-consequence action. C10's "before"
prevents it if taken literally. It does not name the store.

## Corpus

Unchanged at level-3. Release is not a classification. Approving a
withheld operation does not add a case: the applied tier is still 3 and
the disposition of the agent's request is still `withhold`. The execute
half is a second request that is not a new classification, which is
what the draft README already said the format cannot hold.

## Failure

A 500 or an unreachable backend after approval is a terminal `failed`
row. One attempt. The approval remains. Re-attempt is a person.

No NEW-MATTER. Service-identity execute, lazy expiry, and attribution
headers that are not authorisation were the model; they are now code.
