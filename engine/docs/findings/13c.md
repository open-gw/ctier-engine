# 13c — reduction by client entitlement

13b concluded that Keycloak 26.3.3 does not enforce scope reduction at
token exchange. The evidence was narrower: re-exchange restored
`operation-initiatePayment` because the **client was still entitled to
it**. Keycloak bounded the token against the requesting client's
entitlement, not against the subject token's lineage. That is a
different mechanism. This task used the second client 13b
pre-authorised and did not use.

## Part 0 — a defect E1 found and did not fix

`generate()` emitted every classified operation as a **default** client
scope. Default scopes are re-attached on every grant, including
exchange, so an operation scope emitted as default cannot be reduced
by a `scope=` parameter, an executor, or a profile. E1 held in 13b
only after the live fixture called `make_operation_scopes_optional`
over the Admin API. The imported realm and the generator had diverged;
the next regeneration would have silently reintroduced the condition
that makes reduction impossible.

That is now a generate-time fact. Identity (`ctier-identity`) stays
default so `cid` still lands. Operation scopes are optional, never
default. E1 was re-run against that generated configuration, without
the Admin-API move, and still holds.

## E4 — the only experiment

Same shape as 08c and 13b. Live, `pytest --live`, Keycloak 26.3.3
arm64, imported realm JSON. `agent-sub-balance` is entitled to
`operation-getBalance` and nothing else.

| Step | Hypothesis | Observed |
|---|---|---|
| a | Exchange the parent token into `agent-sub-balance`; token carries `operation-getBalance` only | **Holds.** 200. `scope` was exactly `operation-getBalance`. `azp` was `agent-sub-balance`. |
| b | Same exchange, explicitly requesting `operation-initiatePayment` | **Holds, refused.** 400 `invalid_scope` / `Invalid scopes: operation-initiatePayment`. Not issued-without — Keycloak rejected the grant. |
| c | Re-exchange the token from (a), requesting `operation-initiatePayment` | **Holds, refused.** 400 `invalid_scope`, same description. This is the step that failed in E2 when the client was still entitled. |
| d | `POST /payments` at Kong with the token from (a) | **Holds.** 401. Control that Kong accepted the token: `GET /accounts/…/balance` was 200 (`cid` still `ctier`; `aud` is not what the jwt plugin checks). |
| e | Control: the parent client exchanges for `operation-initiatePayment` | **Holds.** 200, token carries the scope. A global refusal of every exchange would have looked like (b)/(c). |

**Falsified if** `agent-sub-balance` obtained `operation-initiatePayment`
by any route, or if the entitlement restriction could not be expressed
in imported realm JSON. Neither happened.

**Expressibility.** Separate from the mechanism. The client, its
optional-scope set, `standard.token.exchange.enabled=true`, and the
audience mapper that puts `agent-sub-balance` on the parent's `aud`
are all realm-JSON fields. Standard token exchange V2 requires the
subject token to list the requester in `aud` unless the requester is
exchanging its own token; that mapper is importable. Fine-grained
admin permissions were not needed. No console-only switch.

E4 held. `feat(generate)` emits the sub-agent client, its
entitlements, the exchange attribute, and the audience mapper,
byte-identical to the realm that ran.

## Claims dump

An exchanged token from (a) carried `azp`, `sub`, `cid`, `iss`,
`scope`, `exp`, `iat`, `jti`, `typ`. It did **not** carry `act`, and
it carried no other reference to the parent client or the subject
token it came from. `azp` is the requester (`agent-sub-balance`);
`sub` is the service-account UUID. The ledger that attributes Tier 3
to agent plus approver can evidence the actor on this credential; it
cannot evidence the chain the credential came through. That is a
record, not a gate.

## For the specification

Two things for a later spec task. Not done here.

**The `standard` profile is described wrongly.** `spec/conformance.md`
defines it as assuming *"an authorisation server enforcing scope
reduction at token exchange"*. E4 held: the enforcement is by client
entitlement, not by lineage. A real mechanism, reached by a different
route. The description should say which.

**Delegation-chain integrity currently has no implementation on either
profile.** Standard-as-lineage is undeployable on 26.3.3 (13b E2).
Constrained was deliberately not built. Both were the right call
individually. Together they leave ADR-003's third item empty while the
spec describes two profiles, and a reader of the evidence section
would not know it. A governance specification that overstates its own
coverage is the specific failure this project exists to argue against.
