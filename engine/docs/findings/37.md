# 37 — the live suite covers what was recorded, not only what was sent

Date: 18 September 2026. Requires 35. Did not edit the spec.

## The wrong division

Tasks 19 and 20 scoped the second suite to *the boundary*, and told
it not to assert tiers or custody internals because the corpus owns
those. The exclusion was right. The name and the scope were not.

The split that actually matters is how an assertion is evaluated:

| Artefact | Evaluated by |
|---|---|
| `conformance-corpus` | comparing documents, offline, without deploying anything |
| this suite | observing a running deployment |

Headers at a backend and records at a sink are both the second kind.
A record arrives at neither the corpus nor the fixture echo, which
is how 35's APISIX `503` with no Attempt survived ADR-005, a
criterion restatement, and a live test that asserted two `503`s.

## Rename

`boundary-suite/0.2.0-draft` is now `runtime-suite/0.3.0-draft`. The
Python package path stays `ctier.boundary` (the probe header
`x-boundary-probe` is on the wire). The schema id is the name that
had to move.

There is **no compatibility shim** for `boundary-suite`. The draft
has no external consumers. Task 31 established what shims cost, and
the deprecation table in `docs/portability.md` is empty and stays
that way. Absence of a row is a decision, not an omission.

## Record assertions

Presence (`recorded`) and absence (`unrecorded`), gated on
`recordSource`. Matching is against the record schema. A
schema-invalid payload and a valid payload with the wrong
`appliedTier` are different failures.

Four cases, Kong and APISIX: custody-down first (35's regression),
Level 1 observe, Level 2 execute, withheld-then-approved.

## Record-source contract

`record-source/0.1.0-draft`: `GET {recordBase}/records` returns
`{ "records": [ … ] }`. Custody's `/v1/ledger` and the gateway log
are two transports for that array. A second implementation stands
the GET up; it does not reimplement log scraping unless that is its
sink.

## Part 5 — demo reset and Keycloak

34's first live run died on leftover APISIX Keycloak (port 19400).
`reset_rigs` is `docker compose -p ctier-kong-live|ctier-apisix-live
down -v`. Keycloak in those compose files has **no data volume** —
only a bind-mounted realm import — so tearing down the live project
clears the process that held 19400 and the next start re-imports.
That is the state that bit 34.

It does **not** tear down a differently named leftover project
(29 recorded `ctier-apisix-probe`). The second-run guarantee holds
for the live demo projects, not for every compose file that might
bind 19400.

## Observation

The suite that would have caught 35 did not exist because its scope
was drawn around *where the data goes* rather than *how the
assertion is evaluated*. That is the same defect as naming a
mechanism where a property was meant — applied to a test artefact
rather than to a specification one, and found the same way: by
something slipping through the gap the wrong division created.

Seven artefacts now. Other boundaries in this project drawn by
subject matter when they should have been drawn by method are worth
one pass: sink vs record type (29 had to say the gateway log is an
Attempt sink), and "boundary" vs "runtime" was this one.
