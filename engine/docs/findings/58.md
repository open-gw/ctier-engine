## Part 1 — which surface is normative

The general question is not settled. The task did not pick
a surface because it was easier to emit.

Spec 1.24.0 `README.md` Response identifiers: the tokens a
client can observe are body `status`, body `agentAction`
"(mirrored on `X-Agent-Action` when that header is emitted)",
and the HTTP status. The body is the identifier. The header
is a mirror when it is emitted. That is not "always" and not
"never".

`headers.md`: an implementation that satisfies C5 by the
`202` mechanism MUST emit `X-Agent-Action` on 202. One that
satisfies C9 by the `423` mechanism MUST emit it on 423.
Another mechanism states itself instead. Additive evolution
does not enlarge that MUST. The example yaml lists
`X-Agent-Action` on `PendingAuthorization` and does not list
it on `AgentSuspended` (it lists `X-Incident-Id`). The named
C9 mechanism in `headers.md` and the example schema disagree
about the header. That is a spec-author item, not an engine
choice.

What this engine does with what *is* settled: C5 202 and
C9's named 423 emit the header as the body's `agentAction`.
`327d075` made both engines consistent with that MUST.
APISIX compiled T4 and floor-escalation T4 had omitted the
mirror; `fault-injection` now carries it. Other dispositions
may omit the header. When both surfaces are present, they
must name the same instruction. A header-only client that
sees nothing on a 403 still cannot be told, from `spec/`,
that the engine is wrong.

## Part 2 — what a Tier 4 handover carries

C9 is no resume under the agent's identity. 48 gave
`X-Incident-Id` a stated trust status: MAY, not a join key.
C9 forbids a correlation identifier on this disposition.
`incidentId` is not on the wire. This engine does not emit
it. `8746a70` records that; it did not add a field.

What correlates a handover today:

| Engine | On the wire | What correlates |
|---|---|---|
| Kong | `423`, `agent_suspended` / `autoResume: false` / `halt_and_hand_off`, and `X-Agent-Action`. No `incidentId`. No `X-Incident-Id`. No `correlationId`. | A `refuse-and-suspend` decision whose `correlationId` the client never sees. |
| APISIX compiled T4 | `423`, the same body, via `fault-injection`, and `X-Agent-Action`. | Nothing. Stock abort writes no decision. Floor-escalation T4 exits before the ledger POST. |
| APISIX C2 T4 | `423`, the same body, and `X-Agent-Action`. | Nothing on a record the client can see. |

C9 does not need `incidentId` on the wire. The property is
that nothing names a resume handle. A named header with
trust status implies it travels; it does not. MAY is not
MUST. The 423 goes out, and the only link — where one
exists — is in a record the client never sees.

## Part 3 — three smaller

Closed `status` / `agentAction` sets live in
`ctier/identifiers.py`. Generate and custody import them.
Kong `handler.lua` still concatenates the same JSON at
module load; a test reconstructs those strings against the
Python definition. Emission sites do not mint.

Leftover literals: the Lua header names and values on
refuse paths (`X-Agent-Action` / `halt_and_hand_off` /
`continue_task_without_this_step`). They are the same
tokens. Apigee `RF-Provisioning` still writes
`X-Agent-Action` on 403 as a literal; `required_instruction_headers`
would omit it. That artefact is not a live engine.

`provisioning_defect` matches 1.24.0: Level 2 cannot
withhold Tier 3; an excluded operation reached by a live
token. Not C12's English "provisioning defect" (that miss
is `unassigned`). Composed-but-unassigned without custody
is still C2's Tier 4, not this token.

`_UNAUTH_BODY` was an unused APISIX constant,
`{"status":"unauthorized","agentAction":"halt"}`. It was
never referenced. JWT already refuses before that path.
`7dcf559` removed it, not wired. Kong's `UNAUTH_BODY` is
a different constant and is used on 401.

## Part 4 — assert the pairing

Runtime suite since 37 asserted presence and records. It
never asserted that two fields describing the same fact
agreed. 41 was the wrong fact in a right-shaped record.
This is two surfaces right-shaped carrying different facts.
The shared root is per-field assertion: a defect in the
*relationship* between two fields is invisible.

`evaluate_instruction_pairing` asserts the pair. A conflict
fails. C5 202 and C9's named 423 also require the header.
Absence on 403 / 401 / 503 / unassigned is not a failure.
A test that checked each field exists would have passed
while they disagreed. `e19cad6` is that pairing, not
separate presence.

What else is asserted field by field and only means
something in combination: `recorded` without which record
type (41); `expect.status` without the body `status` token;
`X-Incident-Id` present without whether it is the join key;
`retryable` without `agentAction`; `correlationId` on the
body without the header of the same name. Those pairs are
not this task.
