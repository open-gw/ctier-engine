# 06a — bounds escalation on the Apigee target

## The gap

Task 06 compiled an Apigee bundle: header stripping, the default tier, the
composition stamp, one conditional flow per classified operation, and fault
rules per disposition. It never mentioned bounds. The Kong plugin in 08b
compares a query parameter to `x-ctier-bounds.max` at request time. The 08a
corpus includes `bounds-exceeds-listTransactions`, whose expect follows the
classifier (applied tier 3), not declared-plus-one.

That was a gap in 06's instruction, not a dialect difference. Left open, an
Apigee miss on that case in 08c would have two causes: the missing comparison,
and whatever 08c exists to isolate. The comparison is now emitted.

## Semantics taken from `exceeds_declared_bounds`

The nested condition is emitted only where both `parameter` and `max` are
declared. A one-sided `x-ctier-bounds` object produces no bounds step — not a
condition that never fires. Excluded operations likewise get no bounds path.

The unexceeded path leaves the compiled floor untouched. The exceeded path
assigns the escalated integer, resolved at generate time: one tier up, never
past 4, never a lower value than the floor. `AM-Tier-listTransactions` writes
`2`; `AM-Tier-listTransactions-bounds` writes `3`. There is no arithmetic in
the proxy.

A request that omits the parameter does not escalate. A non-numeric value does
not escalate. Both fall out of a single numeric comparison
(`request.queryparam.<parameter> > <max>`): Apigee treats an unresolved
variable and a failed numeric coerce as a false condition. No `!= null` guard
was added; that would be a second predicate the reference function does not
have.

## Floor on bounded operations

`listTransactions` is declared 1; its criteria compute 2. The classifier takes
the max, then raises once. Escalating `x-ctier-tier` alone would assign 2 and
miss the handwritten expect of 3. Bounded operations therefore compile
classifier stage 2 (the higher of declared and computed) as the unexceeded
assignment. Unbounded operations still compile `x-ctier-tier` as task 06 did.
Kong still starts from the declared field; that remaining miss is oracle vs
Kong.

## What the condition syntax could not express

Python `int()` is not Apigee's numeric comparison. `int("abc")` and a failed
coerce both refuse to escalate, so the reference's named edges hold. The
functions part company on strings Python rejects and Java accepts as a number:
`101.0`, `1e2`. Expressing `int()` exactly would take a script or a callout.
The target stays declarative. Those inputs are not in the corpus.

No JavaScript, no callout.
