## Identity versus attribution

Custody stores enough to replay the request. It does not store the agent's
credential — not the bearer token, not a refresh token, not anything that
authenticates. A persist that carries an `Authorization` header stores
nothing derived from it. The enforcement point passes the token's `exp`
claim as a number; the deadline is recorded then, and is not recomputed
later from something that was never kept.

The consequence, for task 10: **custody executes under its own service
identity, with the original agent and the approver recorded as
attribution.** The backend sees custody; the ledger sees who asked and
who authorised.

That pair is the whole argument:

> **Tier 3** executes under the system's identity, with the agent and the
> approver recorded. **Tier 4** executes under the human's own credential.
> In Tier 3 a named person authorised an action; in Tier 4 a named person
> performed one. The record says different things and it should.

## What C5 did not mention

C5 was written before anything implemented it. Building the `202` against
it turned up a short list that belongs on the contract, not as folklore:

- **Who constructs the body.** C5 names the properties. It does not say
  the enforcement point must not invent them. Custody returns the complete
  `202` body and headers; Kong relays them. Apigee's fault policy copies
  `custodyPending.content` rather than embedding a JSON literal. One
  implementation, same reasoning as compiling the decision rather than
  the declaration.
- **`authority`.** The solution design's 202 row includes the authority
  class from `x-ctier-handoff`. C5 does not. The body carries `authority`
  when the operation declared one, and omits it when it did not. The
  reference document's Tier 3 operations have no handoff; inventing a
  class would have been a lie.
- **`userMessage`, `classifiedTier`, `expiresAt`, `correlationId`.** All
  on the example schema and the solution-design row; none in C5's
  sentence. The deadline is `min(credential remaining lifetime,
  configured review period)`, from the passed `exp` value.
- **`pollUrl` is omitted.** The example schema lists it as optional. C5
  plus the agentAction ("stop and report, not retry and not poll") mean
  emitting a poll URL would invite the thing the response exists to
  prevent. The published `agentAction` const is
  `continue_task_without_this_step`: continue the rest of the task; do
  not resubmit this step. A new action string was not needed.
- **Headers that accompany the body.** `Cache-Control: no-store`,
  `X-Agent-Action`, `X-Correlation-Id`, `X-Ctier-Tier`. No `Retry-After`.
  C5 names the absence of `Retry-After` and does not name the rest.

The unavailable path is not C5. It is ADR-005: `503`, `retryable: true`,
`Retry-After: 5` (an explicit five seconds, not an HTTP-library default),
agent not suspended. It does not reuse the Tier 4 body or the
provisioning refusal.

Kong's plugin schema takes `custody_url` and `custody_timeout_ms` as
optional top-level fields, not a nested record. A nested record with a
required `url` is materialised empty when omitted, then fails validation
— Level 2 configs would not load. The *generator* configuration is still
a `custody` block; the plugin encoding is Kong's constraint, not a
governance decision.

SQLite is v1-only. The solution design already lists a durable store as
post-v1.

No NEW-MATTER. Relaying a body constructed in one place, deriving a
deadline from an `exp` value, and executing later under a service
identity are the model as specified, now built.
