# 13h — finish the rename, and disambiguate the column

13f renamed the field in the record schemas. It stopped at the schema
boundary. Six surfaces still called the deployment digest
`composition`, and custody's pending column held two meanings with no
marker.

## Part 1 — the discriminator

The ledger already distinguishes. Decision and Attempt payloads carry
`ctierSchema`: `decision-record/0.1.0` with field `composition` against
`0.2.0` with `deploymentDigest`. `test_old_and_new_ledger_rows_are_distinguishable_by_ctier_schema`
inserts a 0.1.0-shaped payload through SQL (validate_record only knows
0.2.0) and a current record through the constructor. The stored hex is
not converted. There is nothing to convert it from.

Custody pending did not. The column was `composition TEXT NOT NULL`,
with no schema version on the row. Rows written before 13g carry a
composition digest; rows written after carry a deployment digest. Same
column, two objects. A discriminator `digest_schema` was added. The
value column is `digest`. Every existing row is backfilled as
`composition`, bounded by the migration point, not by inspecting the
hex — the two objects are incomparable by construction.

No committed sqlite files existed to backfill. The migration copies
every pre-existing row; tests open a pre-13g file of **2** rows and
observe 2 backfilled, values unchanged. New writes stamp
`digest_schema=deploymentDigest`.

## Part 2 — the header is not in the spec

Spec 1.4.0 does not name `x-ctier-composition`. `spec/extensions.md`
lists the `x-ctier-*` keys the description and the qualified spec
carry. The header the gateway emits to an upstream backend is not
among them. Renaming it is not a specification change. A trust-boundary
header that no specification describes is itself the finding.

## Part 3 — boundaries

`x-ctier-composition` → `x-ctier-deployment`. Kong plugin config
`composition` → `deployment`. Apigee `AM-Composition` /
`ctier.composition` → `AM-Deployment` / `ctier.deployment`. Review
queue field `composition` → `deployment`.

The header is emitted both ways through engine 0.3.0. A backend
correlating on the old name keeps working; a backend written against
the new one works immediately. Config keys and ingress fields take
the other direction: accept the old name, warn, remove at 0.3.0.
Generate writes only the new names.

## Part 4 — one table

`docs/portability.md` lists every shim, what replaced it, which
version removes it, and which release line that version belongs to.
Record schema 0.2.0 and engine 0.2.0 remain different milestones.

## Part 5 — what does not change

| Surface | Keeps | Because |
|---|---|---|
| compose manifest, coverage report | `compositionDigest` | compose-time; compose cannot see agent identities |
| conformance corpus document field | `composition` | C13 of the API the cases classify, not a ledger field |

## The rename that stopped at the schema

13f renamed the field in the schemas and treated the rename as done.
It was not. The value appears in the record schemas, the Kong plugin
config, the header the plugin sets, the Apigee variable and policy,
the custody pending column, the review queue, and the generated
bundle metadata — seven places, of which the schemas are one. Nothing
in the repository listed the other six.

A generated-artefact inventory kept beside the generator would have
caught the Kong key, the Apigee names, and `ctier-generate.json` the
next time someone regenerated. It would not have caught the custody
column or the Lua `set_header` unless those were listed as surfaces
the compiled value reaches, and a markdown list of those surfaces
goes stale the first time someone adds a header and does not update
the list. The test that walks the artefacts, the store columns, and
the review queue — and that names its two exceptions as a list
someone must edit — is the inventory that fails closed. A document
next to the generator is useful as a map. It is not a substitute for
the test.

## NEW-MATTER

None. A discriminator on an existing column, and a rename of names
the specification does not use.
