# 11 — the ledger, and C10's first exercise

C10 has never been built against. The criterion says decisions are recorded
before they are acted on. That sentence was true of an engine sitting in the
request path, writing a row, then returning a verdict. The engine no longer
sits there.

## What is actually true

The decision is made at deploy time, when the generator writes a tier into
the compiled configuration. That precedes every subsequent action by a much
larger margin than a synchronous write at request time would. What is written
at request time is **evidence of a decision already made**, not the decision
itself. Asynchronous recording is fine provided it is durable; fail-open
recording is a gap in the evidence, not in the decision.

That is the hypothesis, and it holds. C10 as written is wrong about the
*when* of the write. It is right about something stricter: **no operation
executes without a decision having been made**. The compiled architecture
makes that structurally true. Restating C10 that way would strengthen the
claim rather than weaken the criterion. The spec change is a later task.

Per disposition, relative to the target being called:

| Disposition | Where the decision is made | What is written at request time | Before the target? |
|---|---|---|---|
| `execute` (T1, T2) | generate, into plugin `tier` | a Decision, POST `/v1/ledger`, fail-open, only if `custody_url` is compiled (level-3) | the POST is issued in `access` before proxying; a missed write does not stop the proxy |
| `withhold` (T3) | generate, into plugin `tier` | a Decision, written by custody after persist, before the `202` | the target is not called at request time; persist is the action, and the Decision follows the insert |
| `refuse-and-suspend` (T4) | generate | a Decision, same fail-open POST, then `423` | nothing is routed |
| `refuse-provisioning` | generate (`excluded`, or T3 at level-2) | a Decision, same fail-open POST, then `403` | nothing is routed |
| Attempt (ADR-005) | not a classification | an Attempt, JSONL on a shared volume, then `503` | nothing is routed; applied tier undetermined |

Level-2 compiles no `custody_url`. A Tier 1 request at level-2 executes
with no request-time record at all. That is not a C10 violation on the
compile-time reading. It is a violation of the sentence as written.

No executing disposition satisfies "recorded before acted upon" as written,
if that sentence means a durable request-time write that gates the action.
T1 and T2 fail-open: the target is called whether or not the write lands.
T3's execute is the closest: a Decision already exists from persist, long
before custody calls the backend, and an Outcome is written after the fact
by definition. Gating T1 on custody being up would put custody back on the
request path, which is the architecture C10's original wording assumed and
ADR-004 abandoned.

## Part 3 properties

Both held against the natural implementation. They are not findings.

**3.1** No Decision, Attempt or Outcome contains a substring of the
`Authorization` value, or a field that would carry one. `credential_exp`
stays on the pending row — it is a value taken from a token — and is not
copied onto the ledger. The pending store is not a ledger record.

**3.2** Ledger tables are INSERT only. A withhold-then-approve-then-execute
produces a Decision and an Outcome with the same `correlationId`. The
pending SQLite row still mutates (`pending` → `executing` → `executed`).
That is custody context, not the ledger. Conflating them is the thing C8
warned about and the thing this task refused: one table with nullable
columns, standing in for three types.

## What else C10 did not say

The pattern from C5, C6, C7 and C9 was: a gap that appears only when
something implements the criterion, and the plain reading points the unsafe
way. C10 is the last criterion that had never been built against. The
pattern holds, once, and then it runs out of instances.

The unsafe reading of C10 is **execute, then write the decision only if it
succeeded**. For Tier 3 that would hide a failed high-consequence action;
task 10 already refused it, and the Outcome exists specifically so a failure
is visible. For Tier 1 the unsafe reading is executing with no evidence at
all, which fail-open recording permits and which level-2 does by
construction. C10 did not distinguish the decision from the evidence of it,
so it could not forbid one without appearing to require the other.

Other things the sentence does not say, now that it has been exercised:

- **Recording is not a classification.** The conformance corpus is unchanged.
  A Decision is not a fourth adapter output.
- **An Attempt is not a Decision with a null applied tier.** ADR-005 already
  said this. The schemas enforce it: `appliedTier` is an integer on a
  Decision and `null` on an Attempt.
- **The classifier's `"refuse"` is not a ledger value.** Corpus
  `refuse-and-suspend` is. Writing `"refuse"` would have been the C8 error
  in miniature: a convenient alias that collapses two meanings.
- **Attempt recording is best-effort.** If the JSONL sink is down alongside
  custody, that window has no record. ADR-005 says so rather than implying
  a guarantee. The live test exercises the case where custody is down and
  the volume is not.
- **`GET /v1/ledger` is a read surface, not an agent-facing affordance.**
  Nothing on the `503` points at it. 1.1.8's no-URL rule still holds.

## The fallback file

When persist cannot reach custody, Kong cannot POST an Attempt to it. The
enforcement point appends a JSON line to a shared volume;
custody ingests the file when it next starts (and on `GET /v1/ledger`).
That mechanism is how ADR-005's Attempt exists at all in the case the ADR
is about. It is not in the specification, and it is not a classification
rule. If it belongs in `docs/NEW-MATTER.md`, it is this: recording a
refusal to classify by writing a local log the policy service will ingest
when it returns, rather than requiring the unavailable service to have
received the record.
