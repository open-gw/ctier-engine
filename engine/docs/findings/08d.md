# 08d — classification is not disposition

## What 08c actually found

The first live corpus run was 24 cases, 18 agree, 6 disagree. Every
disagreement was the same shape: the classifier said `withhold` at tier 3,
Kong said `403` provisioning refusal. The dashboard would have kept those
six red forever, with a footnote that they were "out of scope until
custody." A conformance suite that permanently expects failure stops being
read. An unread suite is worse than no suite, because it still looks like
coverage.

The six were not a Kong defect and not a classifier defect. They were a
defect in the harness's own expectation model. That is a good sign. A
harness whose first contact with a real gateway found a hole in *itself*
is doing the job it was built for. The alternative — treating the red as
known, then tolerated, then ignored — is how coverage dies.

Both implementations were right. A Tier 3 operation deployed without
custody is a provisioning defect. That is what the model says and what
task 06 specified. The classifier classifies; it does not know what the
deployment has installed. The corpus had one expected disposition per
case and no way to say which deployment it assumed.

## The split

Classification answers what the operation *is*. Disposition answers what
happens to it. They are not the same function.

| Tier | Level 2 — no custody | Level 3 — custody deployed |
|---|---|---|
| 1, 2 | execute | execute |
| 3 | **provisioning refusal** | **withhold** |
| 4 | refuse and suspend | refuse and suspend |

Same classification, different outcome, both correct. Exclusion is
`refuse-provisioning` at either level; it is not a row in that table.

`expect.appliedTier` is asserted on every case, regardless of level. That
is the classification claim, and it is deployment-independent. All six of
the 08c disagreements already agreed on tier 3. What differed was
disposition.

`expect.disposition` is asserted per deployment level, declared by the
run (`deployment: level-2` or `level-3`). Where a case's disposition
varies by level, the mapping is `dispositionByLevel` rather than two
copies of the request. A mapping with no entry for the declared level is
a corpus error, not a skip — silently skipping is how the six become
invisible instead of green.

The classifier is unchanged. `Classifier.classify` still maps Tier 3 to
`WITHHOLD` unconditionally: Level 3 by construction. It is the oracle for
classification. `ReferenceAdapter` takes the run's deployment level and
projects the classifier's *tier* to the disposition that level implies.
Exclusion is applied as `refuse-provisioning` from the classifier's
disposition, not from tier 4, so it is not collapsed onto
`refuse-and-suspend`. Disposition-by-deployment is a projection at the
edge, not a new branch inside the classifier.

That distinction is the whole point: **the classifier decides what the
operation is; the deployment decides what happens to it.**

## The 403 does not classify

Kong's observation table mapped `403` to applied tier 4. Exclusion and
Tier 3 without custody share that status. Inferring the tier from the
status reintroduces the same conflation the corpus just shed: it would
keep reporting those six as classification disagreements (3 vs 4) after
the dispositions already agreed.

`403` is a disposition (`refuse-provisioning`). `appliedTier` on that
observation is filled from the spec so the comparison is what the proxy
*did*, not a fake T4. Execute paths still reveal the tier through the
echo. `423` still means refuse-and-suspend at 4; `202` still means
withhold at 3. Those statuses are not shared.

## The live re-run

Same rig as 08c: Kong 3.9.3 DB-less, mock echo, plugin as deployed, no
debug variant. Corpus `0.2.0-draft`, `deployment: level-2`.

```
08d differential: cases=24 agree=24 disagree=0 deployment=level-2
```

C11 still agrees (`PUT /config/feature-flags` with `x-ctier-tier: 1`
returned 423, `backendReached: false`). The six former reds agree at
applied tier 3 and `refuse-provisioning`.

The default suite is unchanged: `pytest -q` from `engine/` with sockets
blocked and no containers. This live run was `pytest --live`.

## What the Level 3 half will need

Do not discover this mapping again from a red run.

When custody exists, the Level 3 claim is exercised by declaring
`deployment: level-3` on the corpus and on `ReferenceAdapter`. The same
cases, the same `appliedTier`, the other half of `dispositionByLevel`:
Tier 3 expects `withhold`. A green Level 2 run does not prove that row.

Kong cannot exercise it today. The plugin's `custody` flag defaults
false and is never emitted. If it were true, the Tier 3 branch would
fall through and *proxy* the request — withhold (`202`) is not
implemented. Level 3 therefore needs, at least:

- a custody component the enforcement point can consult
- an actual withhold path (`202`, backend not reached) rather than
  proxying Tier 3
- the C6 sequence the draft README already names: withhold, then
  execute from persisted context — a second request that is not a new
  classification
- a live run against that stack, not a Level 2 run with the mapping
  relabelled

Promotion of this draft to `open-gw/ctier` waits on that run. The
schema has now survived one real gateway and one design correction.
That is closer to ready. It is not the Level 3 half.

No NEW-MATTER. Projecting disposition from a classified tier at a
declared deployment level is the model task 06 already specified,
applied at the adapter edge rather than inside the classifier.
