# 50a — two things before 50 is pushed

Date: 19 September 2026. On top of 50. Did not edit the spec.
Documentation only. No behaviour change.

50 made the only claimed C10 sink auditable. Two facts about that
sink were not written down. Pushing without them publishes a
conformance claim a reader cannot check.

## Part 1 — the sink depends on a log level

The claimed C10 sink is `[ctier-decision]` / `[ctier-attempt]` on
the gateway error log at **NOTICE**. Kong: `kong.log.notice`.
APISIX: `ngx.log(ngx.NOTICE)`.

`error_log ... warn;` is an ordinary production setting. NOTICE
is below it. A deployment that does nothing unusual loses every
record, and C10 with it.

That composes badly with 50. Sequencing detects a missing record
inside a sink. It does not detect a sink that is not there. The
failure most likely to happen in practice is the one the new
mechanism cannot see, and it takes the whole ledger rather than
one row.

Stated where an operator looks: `docs/portability.md`, the same
register as 16d (things this engine cannot enforce). Both
engines. The live APISIX node pins `error_log_level: notice`.
Kong compose does not set a level.

### Startup detection — reported, not built

Should the engine detect at startup that the configured error-log
level excludes NOTICE, and say so rather than run silently?

That is a design question and it is the author's. This task does
not build it. The engine still writes at NOTICE and is silent if
the file will not keep the line.

### Spec author

`docs/NEW-MATTER.md` is not in this repository. For a later task

## Part 2 — what is an emitter?

50 said the sequence is per emitter, not global, and that the
live rig pins one worker on both engines. Those two facts left
the design unstated.

**Counter.** Kong: worker-local upvalue (`seq_state` in
`handler.lua`). APISIX: `ngx.shared.ctier_seq`, keyed
`epoch:{pid}` / `n:{pid}`. The stores differ. The sequence
scope does not: both are per worker. Emitter identity must
include the worker; the epoch string does (`{ngx.now()}-{pid}`).

**Epoch.** Per worker process, minted on first allocate after
that worker starts. Not per node. A worker restart is a new
epoch, not a hole.

**What the one-worker pin hides.** Not contention: Kong never
shares the counter; APISIX incrs a pid-keyed slot. Not
collision: a second worker mints its own epoch and its own
`seq=1,2,3…`. What it hides is interleave. A production node
writes two epochs into one file. `detect_gaps` groups by epoch,
so that is not a hole by design. It has not been run. Do not
build multi-worker verification here.

Under task 33's taxonomy the induced-gap live result is
**Observed under a configuration that is not production-shaped**,
not a plain Observed. Recorded here, in `docs/portability.md`,
`docs/measurements.md`, and `ctier/boundary/README.md`.

### Later — 70 ran two workers

21 September 2026. Task 70 exercised induced-gap with two workers
on Kong and APISIX. Concurrent requests produced multiple
`sinkEpoch` values in one sink; interleave was not a false gap;
dropping a middle seq on one epoch still detected the hole. The
reasoning above held. Default live pin remains one worker; the
two-worker cases live under `test_*_induced_gap_with_two_workers`.
