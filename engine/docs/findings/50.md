# 50 — absence of a record becomes detectable

Date: 19 September 2026. Spec led; this engine follows. Did not
edit the spec. Spec 1.20.0 (origin `open-gw/ctier` 5e3c958) named
the error-log gap. This tree still pins 1.15.0.

The first twenty minor versions found the hole by a drafting
question, not by asking what an auditor would need. Uncomfortable.

## Part 1 — sinks versus diagnostics

Every path a record leaves the enforcement point, and whether this
engine claims it.

| Path | Claim |
|---|---|
| `[ctier-decision]` / `[ctier-attempt]` via `kong.log.notice` / `ngx.log(ngx.NOTICE)` | **C10 sink.** Lands in the gateway error log. Backstop at every level. |
| nginx `access.log` | **Not a sink.** This engine does not write a decision record there. |
| `POST /v1/ledger` | **Not claimed.** Fails open. The error-log line is the backstop. |
| `kong.log.err` / `ngx.log(ngx.ERR)` (ledger failed, persist failed, floor poller) | **Diagnostic.** |
| Kong JSONL `ledger_fallback` | Custody ingest. Not a third sink. |
| Apigee `print()` | **Not a sink** (29). |

Declared in `docs/portability.md`, the PRD, SOLUTION-DESIGN, and
the root README. Not only here.

The brief called nginx access.log the L1–L2 sink. Finding 48
already named the distinction: `[ctier-decision]` is the error
log, written in `access`, not the request line emitted around
the response. This engine kept that sink and sequenced it.
Moving the record to access.log would have changed when it is
written. The named gap was sequencing, not the file.

What that left: one claimed sink. Ledger POST is extra storage
when it succeeds. Diagnostics share the error log and do not
share the claim.

## Part 2 — property then mechanism

A reader holding only the sink's contents can determine a record
is missing.

`epoch=` and `seq=` sit on the line, outside the JSON.
`decision-record/0.2.0` is `additionalProperties: false`. A
schema-valid Decision does not carry the sequence. The sink
does.

Allocate, then emit. Kong: worker-local upvalue, incremented in
`allocate_sequence` before `kong.log.notice`. APISIX:
`ngx.shared.ctier_seq` incremented in `ctier_allocate_sequence`
before `ngx.log`. serverless-post-function loadstrings per
route; `package.loaded` is not an emitter. The shared dict is
node config, same class as `ctier_floors`. Local incr. No
network wait for the number.

Restart mints a new epoch. A reset counter is not a hole. Per
emitter, not global. The live rig pins one worker on both
engines.

Allocation-before-emission changed when records are built. Kong
`record_decision` used to POST first and return `nil` on
failure, with no log line. It now builds `decision_evidence`,
allocates, writes the line, then POSTs (fail-open). APISIX
`_lua_forward_provenance` used to emit the log only when
custody was absent; L3 posted and wrote nothing. It now
allocates and emits before the POST, using the same
`declared` / `applied` / `reason` the hop already computed.

## Part 3 — the suite induces a gap

`induced-gap-is-detected` sends the L2 execute eight times.
The runner drops the middle sequenced record from one epoch
that produced at least three, then `detect_gaps` must report
the missing integer. Not "sequence field present." A single
`seq=1` is not the property.

What it drops: one already-written line from the sink
contents the reader holds. It does not skip emission at the
enforcement point. Allocation-before-emit is the source order
(allocate, then write). The hole is induced after the write,
which is what a lost line looks like.

Kong and APISIX both passed.

## Part 4 — what it does not detect

16d exclusion form, in `docs/portability.md`:

- Wholesale delete or truncate of the sink.
- An emitter that never started.
- Ordering across emitters.

The operator must not treat the sequence as a global log or as
a bound on those three.

## Part 5 — `standard` only

This engine implements `standard`. It does not implement
`constrained`. Said in portability, the root README, the PRD,
and SOLUTION-DESIGN.

The repo described `constrained` as a stated profile
(SOLUTION-DESIGN §9, PRD §2). It did not claim this engine
implements it. Nothing implied `constrained` was built. This
task did not build it.

## Pin tension

`docs/SPEC.md` still names **1.15.0**. C14, C15, and
`governed-set` as a titled identifier are not implemented.
Bumping the pin to 1.20.0 would claim them. This task
implements C10's absence-detectable sink clause as later
releases stated it. Conduct, not a pin change.

## Spec author

`docs/NEW-MATTER.md` is not in this repository. For the spec
author:

- Engine 50 implements the 1.19/1.20 absence-detectable clause
  on the error-log `[ctier-decision]` line. The 1.20.0 version
  entry named that path as a gap. The requirement sentence was
  not rewritten. A second implementation that still writes an
  unsequenced error-log line has not met the clause.
- This engine still pins 1.15.0. It does not claim 1.16.0–1.20.0.
  Vendored schemas remain 1.4.0. The pin and the clause now
  disagree in public. That is the tension. It is not resolved
  by this task.
- nginx access.log is not this engine's C10 sink. If the
  specification meant that file, say so. 48 named the error
  log as the claimed sink; this engine sequenced that.
