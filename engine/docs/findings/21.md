# 21 — can APISIX enforce scope declaratively?

Date: 16 September 2026. Requires 20. Did not edit the spec.

## Candidates

On `apache/apisix:3.13.0-debian`, this rig:

| Plugin | Why considered | Why not the A5 candidate |
|---|---|---|
| `jwt-auth` | Already on the path (A3) | No `required_scopes`. Signed token without the operation scope is 200. |
| `authz-keycloak` | Declarative `permissions`; talks Keycloak | `evaluate_permissions` POSTs `grant_type=urn:ietf:params:oauth:grant-type:uma-ticket` to `token_endpoint` **on the request path**. Measured: echo saw `POST /uma-ticket`. |
| `openid-connect` | `required_scopes` on a verified bearer; `public_key` is a local branch | **Picked.** `introspection_endpoint` / `use_jwks` / unset `valid_issuers` are the network branches and were not used. |
| `opa` / `forward-auth` / `ldap-auth` / `wolf-rbac` | Stock authz | Another server on the request path. |
| `authz-casbin` | Local policy file | Not the compiled JWT operation scope. |

`authz-keycloak` is the likely casualty of ADR-003 and was the casualty. Judged on the wire, not by its YAML.

## A5

**Hypothesis.** APISIX can enforce scope-to-operation using a stock plugin, configured declaratively, with no custom Lua and no per-request authorisation-server call.

**Observed.** **Holds.**

Handwritten standalone YAML, `openid-connect` + `public_key` + `required_scopes: [operation-getBalance]` + `claim_validator.issuer.valid_issuers`. RS256 minted against the in-tree realm key.

| Token | Status |
|---|---|
| signed, with the scope | 200 (echo) |
| signed, `scope: openid` | 403 |
| unsigned | 401/403 |

Echo's `/_harness/requests` showed no `/.well-known/` and no token/UMA hop for those three requests. Discovery is in the plugin schema; `get_discovery_doc` is skipped when `valid_issuers` is set. The URL we emit (`http://127.0.0.1:1/.well-known/openid-configuration`) is a tripwire, not a dependency.

**Falsified if** the missing-scope token were 200, if a hop had appeared, if Admin API were required, or if the check existed only as `serverless-pre-function`. None of those happened.

Missing scope is **403**, not Kong's 401. Same prevention, different stock status.

## If it holds — generate and 13a / 13c

`generate(..., target="apisix")` emits `openid-connect` from the compiled operation name. No new OpenAPI field. Excluded routes keep the plugin and omit `required_scopes`, same shape as Kong omitting `required_scope`. The Lua that decoded `scope` on the accepted bearer is gone.

`jwt-auth` stays for `cid`. Two stock plugins; neither is a scope walk in our Lua.

### Per case (APISIX live)

| Case | Result |
|---|---|
| 13a access-token lifetime | **Holds.** `exp - iat` = 30 s. |
| 13a excluded `closeAccount` | **Holds.** Token does not carry `operation-closeAccount`. `POST /accounts/…/closure` is **403** provisioning, not an `openid-connect` "required scopes" body. |
| 13a T4 then next token | **Does not suspend the grant.** T4 is stock `fault-injection` 423. It does not POST a Decision, so the directory is not told to revoke. The next client-credentials token still carries the scope and is 423 again. A5 is not this hop. Do not add Lua to manufacture it. |
| 13a C8 reject then next token | **Holds.** After `decide(reject)`, the next token is 403 (missing scope). Custody revoke is the same mechanism as Kong. |
| 13a expired withhold | **Holds.** After token TTL, a new token still executes classified Tier 1. |
| 13c E4 (a) exchange into `agent-sub-balance` | **Holds.** 200, `operation-getBalance` only. |
| 13c E4 (b) that client requesting `operation-initiatePayment` | **Holds, refused.** 400 `invalid_scope`. |
| 13c E4 (c) re-exchange requesting payment | **Holds, refused.** 400. |
| 13c E4 (d) `POST /payments` with (a) | **Holds.** 403 (stock missing-scope). GET balance with the same token was 200. |
| 13c E4 (e) parent still entitled to payment | **Holds.** 200. |

## Lua route (not taken)

A5 held, so this was not built. If it had been: same shape as Kong OSS — read `scope` on the bearer `jwt-auth` already accepted, 401, no issuer URL. `_lua_scope` in `generate.py` was that sketch and is removed. Cost: one serverless function per classified non-excluded route; the weak spot 17 already named (payload decode without re-verify). T4→revoke is a *different* Lua (ledger side effect). Kong has it in `handler.lua`. APISIX T4 still does not. That cost is independent of A5.

## Portability

The statement *scope-to-operation binding is not a stock primitive in any gateway tested* is **false** for this APISIX. It remains true of Kong OSS JWT and of APISIX `jwt-auth`. `docs/portability.md` now says that.

This is the second time APISIX's plugin model does in configuration what Kong OSS does in Lua (after `_meta.priority` bracketing). The axis is how much behaviour is configuration rather than code.

### Recommended wording for `spec/conformance.md`

Do not edit the spec from this repo. For the evidence section, something like:

> Scope-to-operation on the request path is a claim about the bearer, not a call to the issuer. Kong OSS enacts it in the `ctier` plugin (401). APISIX 3.13.0 standalone enacts it with stock `openid-connect` `required_scopes` and a configured public key (403); `authz-keycloak` is not this claim, because it obtains a UMA ticket per request. Kong Enterprise `scopes_required` remains unmeasured.

## Configuration versus code

Three engines and one authorisation server have now been tested against the same requirement. APISIX can do declaratively what Kong OSS cannot. The interesting variable is not open-source versus commercial and not one vendor versus another — it is how much of a gateway's behaviour is expressed as configuration rather than as code. Bracketing was the first data point. A5 is the second. That is a better axis for the portability table than either of the two this project has already tried.

## NEW-MATTER

- A5: stock APISIX `openid-connect` `required_scopes` is local JWT scope-to-operation; missing scope is 403 not 401.
- `authz-keycloak` is not an accepted mechanism: UMA ticket on the request path.
- APISIX T4 `fault-injection` does not revoke; C8 reject does. Suspension at T4 on this target is not the authorisation layer until something posts the Decision.
- Recommended `spec/conformance.md` evidence sentence above.
