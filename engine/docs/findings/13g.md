# 13g — emit the deployment digest and close the reconstruction

## ADR-0012 already stated the gap

The Consequences bullet says the digest is taken over the qualified API
description and does not cover declared agent identities, so digest plus
client id does not reconstruct the chain, and that this is a finding of
13e rather than a decision to enlarge the digest there. The decision
text is unchanged. No correction note: an ADR that already named the
gap becoming quietly correct would be the thing this task forbade.

The reconstruction is written in `docs/portability.md`. The ADR still
describes the world as of 13e.

## Canonical form

`deploymentDigest` is `sha256` of canonical JSON (`sort_keys=True`,
separators `(",", ":")`, UTF-8, no trailing newline) of one object:

```
{ "agents": [...], "composed": <qualified spec>, "tiers": [...] }
```

`agents` is the declared identities after the same normalisation
generate uses, sorted by `id`, scopes sorted, `parent` only when
present. `tiers` is every operation's path, method, operationId,
declared tier and exclusion flag, in path/method/id order. File names
are not inputs. Declaration order is not an input.

That is why reordering identities does not change the digest and
renaming a file does not either, and why changing one entitlement or
one tier does. The 13e test that two topologies of the same API shared
a digest is inverted: they do not.

### What is not in the input

Custody URL, target, generator version, `composedAt`, Keycloak
secrets, and the composition manifest's file paths. Those vary by
environment or by how the files were named. Including any of them
would make two people disagree about the same deployment.

The composed document itself can still carry an environment-specific
`servers` URL, and compose can drop an expired recommendation when
`now` moves. Those are properties of the document generate was handed,
not of the digest function. Two generates of one qualified spec
agree. Two composes that produced different qualified specs do not,
and should not.

Nothing in the current inputs fails to serialise: no timestamp object,
no filesystem path, no absolute URL added by generate. `canonical_json`
would raise on a datetime; the corpus keeps recommendation dates as
strings.

## Part 5 — who else reads the digest

| Consumer | Keys, groups, or compares it? |
|---|---|
| Migration proposals (12c) | **No.** Groups by `operationAnchor` and window. Digest is unused. |
| Accumulation scope floor | **No.** Weights declared (else applied) tier by `correlationScope`. |
| Drift manifest | **Yes, the schemas.** `SHA256SUMS` now lists `decision-record-0.2.0` and `attempt-record-0.2.0` with the other schemas. Outcome stayed `0.1.0`. |

Every previously-emitted `composition` value is unequal to the new
digest of the same API, even when the topology did not change: the
serialised input is a different object. Anything that grouped records
by digest across this configuration change will now see two groups.
That is more correct. Migration and the floor do not group that way,
so they will not look like a regression.

The Kong plugin config field is still `composition`. It holds the
deployment digest. New ledger writes stamp `deploymentDigest`. Ingress
accepts `composition` and `compositionDigest` until engine 0.3.0.

Record schema `0.2.0` and engine `0.2.0` are different version lines.
The former is current. The latter is the still-future removal of
`ledger-*` heads. Documented in `docs/portability.md`.

## NEW-MATTER

None. The digest is a wider input to an existing hash. The
reconstruction is the 13e procedure the digest now makes possible.
The single-parent constraint is unchanged.
